# GitHub skills, repositories and tools

Use for discovery, comparison or selection of software, skills and integrations. Resolve the exact repository and component. Classify it as a catalogue, instruction skill, executable tool or complete research system; catalogue popularity does not establish quality of each listed component.

Apply the user's eligibility constraints before deep inspection. Verify current metadata, licence, archived status, relevant release/commit and substantive maintenance. Separate changes to working methods/code and responsive issue/PR handling from automated dependency bumps or link churn. Inspect only the bodies, code and dependencies that could change the decision.

For monthly popularity, name the period, data coverage and measure: net stars, new starring events and timestamps of surviving stargazers are different. Current totals alone do not establish historical growth. Prefer reproducible source data; label gaps, renames and partial months. Do not claim a global monthly ranking from a selected shortlist.

For each eligible candidate, identify the actual missing check/capability it supplies, existing alternatives, dependencies, access/cost, platform compatibility, context burden and conflicting instructions. Evaluate the individual component, not its README promise. Prefer the smallest useful component over importing a whole framework.

Distinguish maintainer claims, independent reproduction and results on the actual model/task. Stars, commits and downloads screen candidates; they do not prove improved answers. A candidate without adequate efficacy evidence remains a candidate for assessment. Stop inspecting one that fails a hard requirement or adds no concrete benefit. Do not install during discovery unless installation was explicitly authorised.
